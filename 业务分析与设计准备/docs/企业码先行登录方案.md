## 1. 背景与问题

### 1.1 现状

药合作系统是一套面向医药营销推广场景的多租户 SaaS 产品，核心使用角色包括：

- **平台运营**：平台侧全量管理
- **药厂角色**：销售管理、合规管理、账务管理等
- **服务商角色**：服务商管理员、工作组长、服务专员
- **服务专员**：一线执行人员，可能同时服务多家药厂

系统当前处于原型阶段，登录流程按"先验人后选组织"设计：手机号/扫码验证身份 → 选择企业身份 → （服务专员）选择服务药厂 → 进入工作台。

### 1.2 问题

技术侧提出：**"先验人后选组织"的方案在现有数据架构下实现成本高**，主要原因是账号体系按企业隔离、没有全局统一的人员唯一标识、跨企业账号合并困难。要求改为"先输入企业编码定位企业，再在企业内做账号验证"的方案。

产品侧需要回应两个问题：

1. 企业码先行这条路能不能走通？用户体验会不会太差？
2. 在"企业码先行"的前提下，账号体系、多企业管理、跨企业切换、服务专员多药厂这些场景怎么处理，才能既满足技术约束、又保持体验上限？

### 1.3 目标

- **设计一套以"企业码先行"为前提的完整登录与账号体系方案**，覆盖从首次登录到日常使用、从账号创建到多企业切换的全生命周期
- **最大化体验灵活性**：企业码只是入口形式，不把整个产品都做死成"账套制"
- **给技术留出清晰的数据模型与接口边界**，便于评审和落地

## 2. 为什么选"企业码先行"

### 2.1 直接原因：对齐现有数据架构

- 历史原因下账号按企业隔离，每个企业有独立的账号命名空间
- 没有全局统一的人员表，手机号、工号都不保证跨企业唯一
- 企业编码是各企业已有的稳定标识，技术上索引清晰、查询路径短

### 2.2 间接收益

- **符合 B 端产品心智**：医药行业客户（尤其是传统药企）对"账套编码"有认知基础，培训成本低
- **企业隔离感强**：登录第一步就是"我们企业的系统"，客户安全感更高
- **利于私有化/专属部署**：同一套代码支持"多租户 SaaS + 单企业专属部署"两种模式，企业码在专属版可以直接隐藏
- **安全边界清晰**：企业层面的频控、限流、封禁都可以在企业码这一层做，不渗透到用户层

### 2.3 体验代价（必须承认）

- 用户多记一个东西：企业码
- 首次登录多一步：先输码再输账号
- 跨企业切换需要记多个企业码，记忆负担增加
- 企业微信/微信扫码的体验需要额外设计（扫码后怎么定位企业？）

### 2.4 设计原则：灵活化补偿

为了弥补体验代价，方案在以下方面做"灵活化"设计，**不让"企业码先行"变成"死板账套制"**：

1. **多形态识别**：企业码、企业域名、企业名称都能定位企业
2. **记忆免输入**：登录过的企业本地记忆，下次直接点选
3. **免密切换**：同一会话周期内切换企业不重输密码
4. **账号打通可选**：同一手机号在不同企业的账号可以关联，但不强制
5. **扫码自适应**：企业微信/微信扫码自动识别企业归属，免输企业码

## 3. 整体流程设计

### 3.1 核心流程：四步登录

```
Step 0 ─── 企业码 ───┐
                     │
Step 1 ─── 凭证 ─────┤   ← 密码 / 短信 / 扫码
                     │
Step 2 ─── 角色 ─────┤   ← 本企业内的多个角色/授权
                     │
Step 3 ─── 服务药厂 ──┘   ← 服务专员专属，多药厂选择
```

每一步都是独立的卡片，视觉语言统一（玻璃拟态 + 光斑背景 + 左侧品牌区），每一步都可以返回上一步。

### 3.2 Step 0 — 输入企业码

**页面定位：** 登录入口页，品牌展示 + 企业定位

**卡片内容：**
- 顶部：Logo + 药合作 / 营销协同管理系统
- 标题：**欢迎使用药合作**
- 副标题：*输入企业代码，开始登录*
- 一个大输入框：placeholder `请输入企业代码，如 BYZK`
- 右侧内嵌「前往 ▶」按钮（渐变主色，和输入框等高）
- 下方小字：`不知道企业代码？联系管理员获取`
- 更下方：演示/试用入口（演示环境才有）

**交互：**
- 企业码不区分大小写，自动 trim
- 回车 = 点击前往
- 输入过程中**不做实时匹配**（安全考虑，防枚举），提交后才校验
- 企业码不存在 → 输入框红边 + 下方提示：「企业代码不正确，请确认后重试」
  - ⚠️ 提示文案统一，**不区分"企业不存在"和"企业已停用"**，防枚举
- 企业码存在 → 平滑过渡到 Step 1

**快捷记忆区（有记忆时显示，无记忆时不显示）：**
- 输入框上方：`最近登录的企业`
- 横向排列 3-5 张企业小卡（Logo + 企业名 + 企业码小字）
- 点击某张卡 → 直接进入 Step 1
- 每张卡右上角有 ×，可删除记忆（只删本地记忆，不删账号）

### 3.3 Step 1 — 凭证登录

**卡片内容：**
- 卡片顶部增加一条**企业标识条**（左对齐 pill）：`🏢 百益健康科技  ·  切换`
  - 点击"切换" → 退回 Step 0
- 三种登录方式 tab：密码登录 / 短信验证 / 扫码登录（和现有一致）
- 对应表单（账号密码 / 手机号验证码 / 二维码）
- 演示账号速查（只展示该企业下的演示账号）

**交互：**
- 验证成功 → 进入 Step 2（单角色直接进工作台，见 3.4）
- 验证失败 → 统一文案「账号或密码错误」，**不泄露"账号是否存在于该企业"**
- 账号锁定/停用 → 统一文案「账号无法登录，请联系管理员」

**企业微信/微信扫码的特殊处理：**
- 如果扫码身份能明确归属某一家企业 → 扫码后直接进 Step 2，**跳过 Step 0 和 Step 1**
- 如果扫码身份归属多家企业 → 进 Step 2 的企业选择版（详见 4.4）
- 如果扫码身份未绑定任何企业 → 提示「该身份未绑定企业，请联系管理员」

### 3.4 Step 2 — 选择登录身份

**页面定位：** 凭证验证通过后，选择本次登录的身份（角色/授权）

**卡片内容：**
- 顶部企业标识条（同 Step 1）
- 标题：**选择登录身份**
- 副标题：
  - 多角色：*该账号在本企业内有多个有效授权，请选择本次登录身份*
  - 单角色：*该账号当前有一个有效授权，确认后即以此身份进入*
- 已验证信息行：王敏 · 138 0912 0104
- 身份卡片列表（每张 = 一个角色授权）：
  - 主信息：角色名（如「药厂销售管理员」）
  - 副信息：数据范围 / 所属部门（如「西北大区」）
  - 状态标签：账号正常 / 即将到期 / 仅查看
  - 选中态：薄荷绿描边 + 右下对勾徽章
- 操作区：
  - 左侧：「使用其他账号」→ 退回 Step 1
  - 右侧：「确认登录」主按钮 → 进入工作台（或 Step 3）

**单角色 vs 多角色：**
- 单角色也走这一页（一张默认选中的卡 + 直接点确认）
  - 原因：保持流程一致，用户形成"选择身份"的心智，未来加角色不用改流程
  - 可以考虑"单角色自动跳过"作为可配置项，但默认不跳

### 3.5 Step 3 — 选择服务药厂（服务专员专属）

完全复用现有 PharmaGate 设计，仅增加企业标识条顶栏。

要点回顾：
- 服务专员账号在企业内有多个"服务药厂"授权
- 选择的是**本次业务数据范围**，不改变所属企业和人员身份
- 支持：单选 + 确认弹窗 / 单药厂直通 / 暂停药厂禁用态
- 进入后可在用户菜单切换服务药厂（免重新认证）

### 3.6 流程图（完整）

```
打开登录页
    │
    ├─ 有本地企业记忆 ──→ 显示最近企业卡 → 点击卡 → Step 1
    │
    └─ 无记忆 / 选"其他企业" → Step 0 输入企业码
            │
            ├─ 企业码正确 → Step 1 凭证登录
            │       │
            │       ├─ 密码/短信验证成功 → Step 2 选角色
            │       │       │
            │       │       ├─ 单角色 → 直接进入工作台
            │       │       ├─ 多角色 → 选择后进入工作台
            │       │       └─ 服务专员 → Step 3 选服务药厂 → 进入工作台
            │       │
            │       └─ 验证失败 → Step 1 显示错误
            │
            └─ 企业码错误 → Step 0 显示错误
```

## 4. 企业码体系设计

### 4.1 企业码定义

企业码是企业在系统中的**唯一短标识**，用于登录时快速定位企业。

**编码规则：**
- 长度：4–12 位
- 字符：大写字母 + 数字（用户输入时自动转大写）
- 命名建议：企业名称拼音/英文缩写 + 行业/地域后缀
  - 例：`BYZK`（百益制药）、`DFHY`（东方恒业）、`HKYY`（华康药业）
- 全局唯一，不区分大小写

**属性：**
- `enterprise_code`：主码，必填，全局唯一
- `enterprise_code_aliases`：别名列表，可选
- `code_visibility`：可见性 — `public`（对外可见，可被检索） / `hidden`（隐藏，只有知道码的人能登）

### 4.2 多形态识别（灵活化核心）

用户输入的"企业码"其实可以是多种形态，后端统一匹配：

| 形态 | 示例 | 匹配优先级 | 适用场景 |
|---|---|---|---|
| 企业主码 | `BYZK` | 1（精确） | 日常登录 |
| 企业域名前缀 | `baiyi`、`byhealth` | 2（精确） | 邮箱自动推导 |
| 企业全称 | `百益健康科技有限公司` | 3（精确） | 新用户首次登录 |
| 企业简称 | `百益`、`百益制药` | 4（模糊） | 演示/试用环境 |

> **正式生产环境建议只开主码 + 域名前缀**，关闭名称匹配（避免被枚举企业名单）。名称匹配作为演示环境和内部测试的便利功能。

### 4.3 企业记忆（免重复输入）

**存储位置：** 浏览器 localStorage（纯前端，不上传服务器）

**存储内容：**
```json
{
  "recent_enterprises": [
    { "code": "BYZK", "name": "百益健康科技", "logo": "/logos/byzk.png", "lastLoginAt": "2026-09-14T10:23:00Z" },
    { "code": "DFHY", "name": "东方恒业推广", "logo": "/logos/dfhy.png", "lastLoginAt": "2026-09-13T16:05:00Z" }
  ]
}
```

**规则：**
- 最多存 5 个，按最近登录时间排序
- 每次成功登录后更新/插入（已存在则移到最前 + 更新时间）
- 用户可以手动删除某个记忆（只删本地，不影响账号）
- 清除浏览器缓存 = 清除记忆

**移动端（App）：**
- 记忆存在 App 沙箱内，换手机不同步
- 可考虑"账号关联企业列表"存在服务端（登录后自动带出该账号所有已授权企业），这是 V2 功能

### 4.4 扫码场景下的企业定位

企业码先行的体系下，企业微信/微信扫码是个特殊场景——用户没机会输企业码。三种处理方式：

**方案 A：扫码身份绑定单企业（推荐，V1）**
- 一个扫码身份（企业微信成员 / 微信开放平台账号）只绑定一家企业的一个账号
- 扫码后直接定位企业 + 身份 → 进 Step 2（单角色直接进工作台）
- 优点：简单、符合绝大多数用户实际情况
- 缺点：一个人不能用同一个微信绑定两家企业的账号

**方案 B：扫码身份可绑多企业，扫码后进企业选择页（V2）**
- 一个微信可以绑多家企业账号
- 扫码后显示"选择要进入的企业"列表
- 优点：灵活
- 缺点：多一步、开发量稍大

**方案 C：扫码 + 企业码二合一（兜底）**
- 扫码后如果身份未绑定任何企业，提示 "请输入企业码完成绑定"
- 相当于把扫码和企业码结合，作为首次绑定的入口

> **V1 实施方案 A + C**（单企业绑定 + 未绑定时输码绑定），V2 再考虑 B。

### 4.5 切换企业

已登录状态下切换企业，不需要重新输密码（在会话有效期内）。

**入口：** 用户菜单 → 「切换企业」

**流程：**
- 点击 → 弹出企业码输入 + 最近企业列表（同 Step 0 样式）
- 选择/输入企业码 → 自动带出该企业下该账号可用的角色 → 选角色 → 直接换发会话进入
- 整个过程不需要重新验证密码/短信

**会话安全约束：**
- 免密切换有效期：同一次登录会话内 2 小时（可配置）
- 超时后切换企业需要重新验证凭证
- 高敏角色（如合规管理员、财务）可以配置为"切换必验证"

## 5. 账号创建与管理体系

企业码先行方案下，账号体系的设计是关键。以下是完整的账号生命周期。

### 5.1 账号模型：人-企业-角色 三层

```
企业 (Enterprise)
  │
  ├─ 部门 / 组织架构
  │
  └─ 人员 (Person) ──── 全局人员表（手机号为唯一标识，可选）
       │
       └─ 企业内账号 (EnterpriseAccount)
            │
            └─ 角色授权 (RoleAssignment)
                 ├─ 角色
                 ├─ 数据范围
                 └─ 生效/失效时间
```

**关键说明：**
- **全局人员表可选**：V1 可以没有，每个企业的账号独立存在
- **企业内账号**是登录主体，登录凭证（密码、手机号、扫码绑定）挂在企业内账号上
- 同一个人（同一个手机号）在不同企业可以有独立账号
- **可选：人员关联**——同一手机号的多个企业账号可以标记为"同一个人"，用于跨企业记忆和关联展示，但不强绑定

### 5.2 账号创建方式

#### 方式一：管理员创建（主流）

- 企业管理员在「用户与组织」页面新建用户
- 填写：姓名、手机号、工号、部门、角色、数据范围
- 系统生成初始密码 / 发送设置密码链接到手机 / 邮箱
- 用户首次登录时强制修改密码

#### 方式二：邀请加入

- 管理员生成邀请链接 / 邀请二维码
- 被邀请人打开 → 输入企业码（或链接里已带）→ 验证手机号 → 设置密码 → 完成注册
- 适用于服务商批量邀请专员

#### 方式三：扫码绑定

- 用户用企业微信/微信扫码
- 首次扫码未绑定 → 提示输入企业码 + 工号/姓名 → 管理员审核 → 绑定成功
- 适用于企业微信场景

#### 方式四：自助注册（可选，通常关闭）

- 用户自行输入企业码 + 手机号 + 验证码 + 个人信息
- 提交后进入"待审核"状态
- 管理员审批通过后才能登录
- 适合开放性高的平台型产品，B 端药企一般不开

#### 方式五：批量导入

- 管理员下载模板 → 填写人员名单 → 上传
- 系统批量创建账号，发送初始密码短信
- 适合上线初期批量建账号

### 5.3 凭证类型

每个企业内账号可以绑定多种登录凭证：

| 凭证类型 | 说明 | 绑定方式 |
|---|---|---|
| 账号密码 | 用户名 + 密码 | 管理员创建 / 自助设置 |
| 手机号 + 短信 | 手机号 + 6 位验证码 | 绑定手机号 |
| 企业微信 | 企业微信成员身份 | 企业微信扫码绑定 |
| 微信开放平台 | 个人微信身份 | 微信扫码绑定 |
| 钉钉 / 飞书 | （按需扩展） | — |

**规则：**
- 一个账号可以同时绑定多种凭证
- 至少有一种凭证才能登录
- 手机号是核心凭证（用于找回密码、短信验证），建议必绑
- 同一企业内手机号唯一

### 5.4 账号状态

| 状态 | 说明 | 能否登录 |
|---|---|---|
| 正常 | 正常使用 | ✓ |
| 未激活 | 新建后未设置初始密码 | ✗（提示激活） |
| 已停用 | 管理员停用 | ✗（提示联系管理员） |
| 已锁定 | 多次登录失败临时锁定 | ✗（自动解锁或管理员解锁） |
| 已离职 | 人员离职，账号保留审计 | ✗ |
| 已删除 | （软删除）归档 | ✗ |

### 5.5 跨企业账号关联（可选高级功能）

虽然企业码先行，但体验上"同一个人在多家企业有账号"还是要方便。

**关联方式：**
- 用户在 A 企业登录后，去"个人设置" → 「关联其他企业账号」
- 输入 B 企业码 + B 企业的账号密码 → 验证通过 → 两个账号关联
- 关联后：
  - 登录任意一家企业后，可以免密切换到另一家（用户菜单「切换企业」）
  - 最近企业列表自动包含所有已关联企业
- 关联只做体验便利，**不合并数据、不共享权限**，每个企业的账号仍然独立

### 5.6 服务专员账号的特殊性

服务专员属于某家服务商企业，但同时服务多家药厂。这个关系在企业码体系下要保持清晰：

- **所属企业** = 服务商（企业码定位的就是这家）
- **服务药厂** = 业务数据范围（登录后 Step 3 选择）
- 服务药厂的增删由服务商管理员和药厂管理员共同管理（现有准入/授权流程）
- 切换服务药厂在用户菜单内完成，不走企业码流程

服务专员 **不需要记药厂的企业码**，只需要记所属服务商的企业码。这是体验的底线。

## 7. 安全设计

### 7.1 反枚举

企业码先行的最大安全风险是**企业码被枚举**，导致企业名单泄露。防护措施：

- **错误提示统一**：企业码不存在 / 企业已停用 / 账号不存在 / 密码错误 → 全部返回模糊文案，不告知具体原因
- **频控（按 IP）**：同一 IP 1 分钟内最多 10 次企业码查询，超限冷却 5 分钟
- **频控（按企业码）**：同一企业码 1 小时内登录失败次数 > 20 次 → 该企业码登录入口临时增加图形验证码
- **图形验证码兜底**：连续 3 次企业码错误 → 弹出图形验证码（V2）
- **隐藏企业码**：企业可设置为 hidden，隐藏后"企业码是否存在"不对外暴露

### 7.2 账号安全

- 密码强度校验（8 位以上 + 字母数字混合，可配置）
- 首次登录强制修改密码
- 90 天密码过期（可配置）
- 5 次连续失败锁定 30 分钟
- 异地登录提醒（短信）
- 支持两步验证（TOTP / 短信，V2）

### 7.3 会话安全

- 会话令牌：HttpOnly + Secure Cookie
- 默认会话有效期：8 小时（可配置）
- 7 天免登录（可选，移动端默认开，PC 默认关）
- 切换企业 / 切换角色 / 切换服务药厂都换发会话
- 登出即时失效

### 7.4 数据隔离

- 所有业务接口都从会话里取 `enterpriseId`，**不接受前端传的企业参数**
- 数据表按 `enterprise_id` 做行级隔离
- 服务专员的数据范围额外加 `serving_pharma_id`
- 跨企业数据查询必须走平台侧专用接口，且有审计日志

### 8.1 PC 端（主端）

- 完整四步流程
- 左侧品牌区 + 右侧卡片布局

- 同移动端布局

## 9. 与现有方案的差异

### 9.1 对比"先验人后选企业"方案

| 维度 | 先验人方案 | 企业码先行方案 |
|---|---|---|
| 登录第一步 | 手机号/账号 | 企业码 |
| 企业定位 | 凭证验证后反查 | 凭证验证前确定 |
| 账号模型 | 全局人员 + 多企业授权 | 企业内账号 + 可选人员关联 |
| 用户记忆负担 | 手机号/账号 + 密码 | 企业码 + 账号 + 密码 |
| 首次登录步骤 | 2-3 步 | 3-4 步 |
| 日常登录步骤 | 2-3 步 | 1-2 步（有记忆时） |
| 跨企业切换 | 自然（同一个人） | 需要企业记忆 + 免密切换 |
| 技术落地难度 | 高（需全局统一账号） | 低（对齐现有隔离架构） |
| 企业安全感 | 一般 | 强（先看到自己企业） |
| 扫码登录体验 | 天然流畅 | 需要额外设计（见 4.4） |

### 9.2 对比"传统账套制"

| 维度 | 传统账套制 | 本方案 |
|---|---|---|
| 企业入口 | 各企业独立域名/部署 | 统一入口，企业码定位 |
| 视觉品牌 | 各企业完全独立 | 统一品牌 + 企业标识条 |
| 多企业切换 | 退出重登 | 免密切换（会话内） |
| 账号体系 | 完全隔离 | 企业内隔离 + 可选人员关联 |
| 数据隔离 | 物理隔离（多库） | 逻辑隔离（行级） |
| 运维成本 | 高（每套独立维护） | 低（一套系统） |

## 11. 开放问题

以下问题需要业务/技术共同确认：

1. **企业码的命名规范？** 系统自动生成还是管理员自定义？有没有命名冲突解决机制？
2. **手机号在企业内必须唯一吗？** 允不允许一个人在同一家企业有多个账号（如多角色）？
3. **初始企业码怎么迁移？** 现有客户有没有在用的编码？要不要沿用？
4. **演示/试用环境要不要开企业名称搜索？** 正式环境建议关闭，演示环境为了方便可以开
5. **服务专员的"服务药厂"列表，企业码方案下展示逻辑变不变？** （本文认为不变，仍然是登录后 Step 3 选择）
6. **切换企业的免密切换有效期？** 默认 2 小时是否合适？
7. **管理员创建账号时，登录凭证怎么发？** 短信链接 / 邮箱链接 / 初始密码告知？
8. **企业微信场景下，员工用企业微信扫码应该自动进入本企业，不需要输企业码——这个流程是否走得通？** （本文方案 A 假设走得通，需要技术确认）

## 附：术语表

| 术语 | 含义 |
|---|---|
| 企业码 | 企业在系统中的唯一短标识，用于登录时定位企业 |
| 企业内账号 | 某个企业下的登录账号，凭证和角色都挂在这里 |

| 服务药厂 | 服务专员的业务数据范围，不属于企业体系，属于业务授权 |
| 凭证 | 登录验证手段，如密码、短信、企业微信、微信 |
| 记忆 | 浏览器/本地存储的"最近登录过的企业"列表，纯前端 |
