# 权限管理模块 AI 提示词（原型落地）

> 用途：投喂给 AI 编码工具（Figma Make / Cursor / Claude 等），在 `重构/业务分析与设计准备` 原型中落地"角色权限管理"模块，并让全站角色差异由权限配置驱动——彻底消灭"每次演示手改字段/按钮/数据范围"的维护成本。
> 提示词自包含，不依赖外部文档。设计依据：《角色权限管理模块设计》（Obsidian）。

---

## 提示词正文（从此处开始复制）

你是一位资深前端架构师 + B 端产品工程师。本项目是 React 19 + Vite + TypeScript + Tailwind CSS v4 + lucide-react 的高保真原型（数据来自 `src/data/mockData.ts` 模拟数据），你需要新增一个「角色权限管理」模块，并用它驱动全站的角色差异。

### 背景与问题

当前角色差异散落在代码各处：`App.tsx` 的 navGroups 静态写死（切角色只有首页变，其他页面所有角色都能进）、按钮显隐靠页面内 if/else、mock 数据单租户单套、角色列表硬编码。每来一次演示就要手工改字段、改按钮、调数据可见范围。**目标：把"谁能看到什么、能做什么"收敛为一处定义、处处派生——以后改角色只改一个文件，换演示场景只切一个预设。**

### 总原则（必须遵守）

1. **单一事实源**：所有权限定义只允许存在于新建的 `src/data/permissions.ts`；菜单、按钮、表格列、首页、角色切换器全部从它派生，任何页面不得再出现硬编码的角色判断。
2. **权限六维**：D1 功能（菜单/页面三态：可见/隐藏/占位）、D2 操作（按钮动作）、D3 字段（V 可见 / H 隐藏 / M 脱敏）、D4 数据范围（ALL_PLATFORM / PHARMA / PROVIDER / GROUP / SELF）、D5 业务规则可见性、D6 审计事件。
3. **数据挂组织**：每条 mock 数据补 `orgPath` 字段（如 `/platform/pharma-01/provider-03/group-12/user-88`），统一过滤函数 `visibleData(rows, role, orgPath)` 做路径前缀匹配，替代任何页面内的手工数据裁剪。
4. 原型层面允许权限判定在前端执行，但代码结构必须按"求值 → 派生"分层（模拟正式系统的权限上下文），方便未来接入后端。

### 任务一：建立权限单一事实源 `src/data/permissions.ts`

定义并导出以下 TypeScript 结构：

- `ROLES`：8 个预置角色（平台运营、系统管理员、账户管理员、药厂管理员、药厂合规管理员、服务商管理员、工作组长、服务专员），每个含 key/label/description/kind(preset)/status。
- `PERMISSIONS`：动作编码字典，格式 `<模块>:<资源>:<动作>`，至少覆盖：`task:package:dispatch`（发包）、`task:package:accept`（承接）、`visit:record:submit`（填报）、`visit:record:audit`（审核）、`compliance:inspection:launch`（随检）、`supplier:admission:audit`（准入审核）、`settlement:confirm`（结算确认）、`config:rule:edit`（规则配置）、`perm:role:assign`（角色调整）、`data:export`（导出）。
- `ROLE_MATRIX`：每个角色的六维权限集——可见页面 id 列表（含三态）、动作编码集合、字段策略表（fieldKey → V/H/M + maskRule）、scopeType、规则可见性。
- `FIELD_POLICIES`：脱敏规则库与字段清单，至少包含：`doctor-anonymize`（医生 → "医生-A"）、`name-mask`（张*三）、`amount-round`（¥1.2万）、`phone-mask`。
- `buildPermissionContext(roleKey, orgPath)`：求值函数，返回 `{ menus, actions, fieldPolicy, dataScope, ruleVisibility }`，字段策略冲突时取最严格。

权限矩阵基准（写成默认配置）：药厂管理员=任务/预算/业务/结算/统计，PHARMA，金额可见；药厂合规管理员=风险/随检/准入/备案/证据，PHARMA，医生 name-mask 之外全可见；服务商管理员=承接/分配/初审/结算，PROVIDER，医生 name-mask；工作组长=填报辖区+初审，GROUP；服务专员=本人填报+我的结算，SELF，医生 anonymize、他人结算字段 H；平台运营=全模块，ALL_PLATFORM；系统管理员=系统管理；账户管理员=用户管理。

### 任务二：全站接线（消灭散落的角色判断）

1. `App.tsx` 的 navGroups 改为由 `buildPermissionContext(role).menus` 派生渲染（保留三态：可见 / 隐藏 / 灰色占位"未开放"）；角色切换器的角色列表从 `ROLES` 读取，不再硬编码。
2. 新增工具函数 `visibleData(rows, role, orgPath)`，给 `mockData.ts` 全部数据补 `orgPath`；拜访管理、推广任务、结算等列表页的数据源改为经过 `visibleData` 过滤——切换角色后列表内容真实变化，不再全量展示。
3. 表格列渲染接入字段策略：医生姓名列对服务商/组长/专员按 `doctor-anonymize`/`name-mask` 处理；结算金额列对无 `settlement:confirm` 权限的角色按 `amount-round` 或隐藏处理。
4. 各页面顶部操作按钮（发包/审核/驳回/结算/导出）改为按 `actions` 集合显隐。

### 任务三：「角色权限管理」模块页面（挂在系统管理菜单下，仅平台运营/系统管理员可见）

1. **角色管理**：角色列表（角色名/类型 预置·定制/状态/挂载人数/最近变更）+ 新建（从预置克隆）、停用（有挂载用户时禁止并提示）；预置角色只读。演示用 mock 挂载数据。
2. **权限矩阵编辑器**：点击角色进入抽屉/页面，分五个页签勾选：功能（页面树三态）、操作（动作编码列表）、字段（字段×角色 V/H/M 三态格 + 脱敏规则下拉）、数据范围（scopeType 单选 + 组织树选点）、规则可见性。保存后调用 `buildPermissionContext` 立即生效——**在本原型中允许真实修改内存中的 ROLE_MATRIX，用于演示"改一处、全站变"**。
3. **用户授权**：用户-角色-组织节点三元组授权列表，支持新增/移除授权行（mock 用户数据）。
4. **以角色预览**：管理员选"角色 + 组织节点"进入只读预览模式：顶部常驻橙色横幅"预览模式（只读）· 以 XX 角色查看"，所有写操作按钮禁用，退出预览回到管理视角。
5. **审计查询**：扩展现有 AuditLog 页，增加权限事件类型（角色切换、授权变更、预览进入/退出、越权点击被拦截），权限模块内的所有操作自动写入审计 mock。

### 任务四：演示场景预设（演示控制条）

新增一个全局"演示场景"切换入口（顶栏或设置抽屉），四个预置场景，每个场景 = 租户组织树 + 数据集 + 预置账号列表：

| 场景 key | 名称 | 预置账号（角色） | 数据故事 |
|---|---|---|---|
| `cnbg-compliance` | 中国生物·合规管控 | 合规管理员、审核员 | 疫苗推广任务 + 若干高风险事件 + 待随检清单 |
| `pharma-sales` | 药厂·销售看板 | 药厂管理员 | 预算-任务包-执行链 + 自营/服务商双队伍 |
| `provider-collab` | 服务商·协同执行 | 服务商管理员、工作组长、服务专员 | 承接任务 + 待分配工作量 + 待初审队列 |
| `platform-ops` | 平台运营 | 平台运营、系统管理员 | 全租户数据 + 规则配置 + 权限模块自身 |

要求：切换场景 = 整包加载该场景的 orgPath 前缀数据与账号列表（mock 中按 orgPath 前缀隔离四套数据故事）；角色切换器只显示当前场景的预置账号；场景之间互不污染。

### 验收标准

1. 新增或修改一个角色的任何权限，只改 `permissions.ts` 一处，全站菜单/按钮/列/数据随之变化；
2. 切换角色后：菜单不同、列表数据经 orgPath 真实过滤不同、医生姓名/结算金额按策略脱敏、操作按钮按动作编码显隐；
3. 在权限矩阵编辑器里改某角色权限并保存，不刷新页面即生效；
4. 四个演示场景一键切换，各场景账号、数据、首页重点不同；
5. 以角色预览模式有橙色只读横幅，写操作禁用，进入/退出写入审计；
6. 角色权限管理菜单仅平台运营/系统管理员可见；
7. 构建无 TypeScript 错误。

### 不要做

- 不要在业务页面里新增任何硬编码角色判断（if role === 'xx'）；
- 不要改动业务页面内部逻辑，只做"数据源过滤 + 列策略 + 按钮显隐"的接线；
- 不做真实后端/登录/持久化，权限修改保存在内存即可；
- 不要把四个场景做成四份重复代码——场景只是数据预设，渲染逻辑只有一套。
