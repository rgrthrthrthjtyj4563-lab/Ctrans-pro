# 服务商准入：双角色菜单与流程优化执行规格

> 版本：V1.0  
> 日期：2026-09-04  
> 目标：将“服务商准入管理”从一个包含全生命周期内容的合规演示页，收敛为可执行的双角色准入闭环。本文可直接交给开发 AI 实施；未在本文明确要求的任务、预算、品种、价目、绩效等功能不改。

---

## 1. 决策与边界

### 1.1 唯一业务闭环

```text
服务商提交准入资料 → 药厂合规审核 → 通过 / 驳回 → 准入结束
                                      ↘ 驳回后由服务商修改并重新提交
```

**“服务商准入”不负责**合同、品种授权、任务分配、履约、结算、复审、冻结、退出、代表备案、绩效、预算和价目表。这些能力保留在原有独立模块，不能再出现在服务商准入页的流程、列表列或详情页签中。

### 1.2 目标登录角色

本次服务商准入模块只保留两个业务视角；现有“药厂销售部门”不再参与该模块。

| 目标角色 | 系统现有登录角色 | 准入职责 | 禁止事项 |
|---|---|---|---|
| 服务商 | `服务提供商` | 维护本企业资料、提交准入、查看驳回原因、修改后重提 | 审核、批准/驳回他人、创建其他服务商 |
| 药厂合规 | `药厂合规部门` | 查看所有提交记录、审核、通过或驳回、查看审批历史 | 替服务商填写/提交资料、修改已通过主体资料 |

> 当前应用仍有三项全局登录切换角色：`药厂销售部门 / 药厂合规部门 / 服务提供商`。本次只将“服务商准入管理”从药厂销售端隐藏；不要删除全局 `Role` 类型或影响其它业务页面。

### 1.3 成功标准

用户打开页面后，10 秒内必须能回答三件事：

1. 我是提交资料还是审核资料？
2. 当前记录的状态是什么、下一步由谁处理？
3. 若被驳回，需要补什么？

## 2. 现状问题与必须移除项

当前页面将尽调、信用、选聘、评级、合同、人员、履约、结算校验、审计等堆叠在“服务商档案”中；页面标题下还有“项目/结算校验”入口和技术函数名。这些内容与最小准入闭环无关，既干扰服务商提交，也让合规审核没有明确待办。

### 2.1 删除或从准入模块彻底移出

| 内容 | 当前表现 | 改造要求 |
|---|---|---|
| 状态 | 草稿、待提交、尽调中、审批中、补件中、准入通过、可合作、复审中、限制合作、冻结、退出等 | 该模块只使用 `待提交 / 已通过 / 已驳回` |
| 指标卡 | 可合作、尽调中、复审中、冻结、高风险 | 删除；服务商端改为“待提交/已通过/已驳回”数量，合规端改为“待审核/已通过/已驳回”数量 |
| 风险评级、尽调、合规信用、选聘 | 详情页签与准入门槛 | 不在本期准入页面展示或录入 |
| 合同、人员、履约结算 | 详情页签和表格列 | 不在本期准入页面展示或录入 |
| 项目/结算校验 | 详情底部入口，显示 `checkVendorEligibility` / `checkSettlementEligibility` | 删除入口、弹窗与相关页面内状态；不得在 UI 暴露技术函数名 |
| 复审、冻结、退出 | 详情操作 | 删除入口和状态，不在此次页面处理 |
| 高风险例外 | banner、例外三要素、特殊审批 | 删除；本期准入不做风险分级 |
| 复杂审批链 | “业务负责人→采购→法务→合规”等文字 | 删除；仅保留“药厂合规审核” |

### 2.2 保留但收敛的资料字段

服务商一次性提交基础主体资料；文件在原型中仍可用文件名文本模拟，不做真实上传解析。

| 分组 | 字段 | 必填 | 服务商可编辑 | 合规可编辑 |
|---|---|---:|---:|---:|
| 基本资料 | 公司名称、统一社会信用代码、法定代表人、注册地址 | 是 | 是 | 否 |
| 联系方式 | 联系人姓名、联系电话 | 是 | 是 | 否 |
| 证明材料 | 营业执照文件名 | 是 | 是 | 否 |
| 审核信息 | 审核人、审核时间、审核意见 | 审核时 | 否 | 是 |
| 驳回信息 | 驳回原因 | 驳回时 | 否 | 是 |

不要要求实际控制人、股权结构、开户行、账号、开票能力、负责人、场地、人员清单、选聘记录或合同资料。统一社会信用代码保持唯一性校验。

## 3. 状态机与权限规则

### 3.1 状态机（唯一事实来源）

```text
草稿（仅服务商本地保存，可选）
  └─ 提交 → 待提交
待提交
  ├─ 合规通过 → 已通过
  └─ 合规驳回（原因必填）→ 已驳回
已驳回
  └─ 服务商编辑并重新提交 → 待提交
已通过（终态）
```

若原型不需要“保存草稿”，可完全不创建草稿记录；服务商填写完资料直接提交，状态从无记录进入 `待提交`。二者只能选一种实现，本次推荐保留草稿以避免填写中断丢失，但草稿不得出现在合规待办中。

### 3.2 按状态权限

| 状态 | 服务商 | 药厂合规 |
|---|---|---|
| 草稿 | 编辑、删除草稿、提交 | 不可见 |
| 待提交 | 只读查看，不可重复提交 | 查看、通过、驳回 |
| 已驳回 | 编辑、重新提交、查看驳回原因 | 只读查看历史 |
| 已通过 | 只读查看审核结论 | 只读查看历史 |

硬规则：

- `已通过` 不可被任一角色编辑、重新提交、驳回或撤销。
- `待提交` 只能由药厂合规操作通过或驳回；驳回原因必填，最少 5 个字符。
- 服务商仅可访问自己的唯一主体记录；不得出现“引入服务商”或“新建服务商”字样。
- 同一统一社会信用代码只允许一条有效主体档案。提交时发现重复，阻止提交并提示“该统一社会信用代码已存在”。
- 审核动作写入不可编辑的历史记录：动作、操作人、角色、时间、意见/驳回原因。

## 4. 两个角色的菜单设计

### 4.1 服务商端菜单

服务商端只暴露完成当前职责所需的内容，首屏默认进入服务商准入。

```text
服务商端
├─ 服务商准入
│  ├─ 我的准入资料
│  └─ 提交记录
├─ 任务执行                 （保留既有独立能力）
├─ 医院拜访                 （保留既有独立能力）
├─ 结算明细                 （保留既有独立能力）
└─ 品种授权                 （保留既有服务商授权能力）
```

服务商端必须隐藏：药厂工作台、预算计划、品种信息、价目管理、系统管理、权限管理、医药代表备案管理，以及其它服务商的全部信息。

> 若现有 `服务商准入管理` 被 `hideForRoles: ['服务提供商']` 隐藏，必须取消该隐藏规则；页面自身再根据角色渲染“我的准入资料”视图。

### 4.2 药厂合规端菜单

```text
药厂合规端
├─ 工作台
│  └─ 待审核服务商数量与跳转入口
├─ 合规管理
│  ├─ 服务商准入审核
│  └─ 医药代表备案管理          （现有独立功能，保持）
└─ 操作日志                     （若当前权限可见则保留）
```

药厂合规端不得显示任务管理、业务数据、品种管理、价目管理、绩效管理、菜单管理、角色管理、用户与组织、执行链路配置等经营/系统配置能力。

### 4.3 药厂销售端处理

药厂销售端在“服务商准入管理”中不显示菜单、不具备路由访问权限、不保留新增或编辑入口。全局角色切换及销售端其它既有页面保持不变。

## 5. 页面规格

### 5.1 服务商端：我的准入资料

#### 空状态

```text
标题：完成服务商准入后即可承接合作
说明：请提交企业基本资料和营业执照，药厂合规部门审核通过后完成准入。
主按钮：填写并提交资料
```

#### 编辑/草稿状态

- 页面标题：`服务商准入`
- 页头说明：`请填写企业基本资料并提交药厂合规审核。`
- 仅展示 §2.2 的三组资料字段。
- 主按钮：`提交审核`；次按钮：`保存草稿`（若保留草稿）。
- 提交失败时，在字段区域上方显示明确缺项，例如：`请补充：营业执照文件、联系人电话`。

#### 待审核状态

```text
状态：待药厂合规审核
说明：资料已于 YYYY-MM-DD HH:mm 提交，暂不可修改。
```

只展示只读资料与“提交记录”，不出现编辑、审核、合同、任务或结算入口。

#### 已驳回状态

```text
状态：已驳回
驳回原因：<合规填写的原文>
主按钮：修改并重新提交
```

驳回原因必须置于页面最醒目的位置，不能藏在抽屉或审计页签中。

#### 已通过状态

```text
状态：准入已通过
说明：已于 YYYY-MM-DD HH:mm 由 <审核人> 审核通过。
```

资料和历史均只读；不显示“可结算”“合同”“任务”等推导性状态。

### 5.2 药厂合规端：服务商准入审核

#### 列表

页面标题：`服务商准入审核`  
页头说明：`审核服务商提交的准入资料。`

列表列固定为：

| 服务商名称 | 统一社会信用代码 | 联系人 | 提交时间 | 状态 | 操作 |
|---|---|---|---|---|---|

筛选只保留：服务商名称/信用代码关键字、状态（待提交/已通过/已驳回）。不要风险等级、服务类型、合同、人员、有效期等筛选。

默认排序：`待提交` 在前，再按提交时间倒序。列表顶部只显示一个待办数字，例如：`待审核 3 家`，不显示 5 张经营/风险指标卡。

操作：

- 待提交：`审核`
- 已通过、已驳回：`查看`
- 不提供“编辑”“提交审批”“准入”“发起复审”“冻结”“退出”“项目/结算校验”。

#### 审核详情

打开一个居中抽屉或弹窗，按以下顺序显示：

1. 状态和提交时间；
2. 企业基础资料；
3. 营业执照文件名；
4. 提交历史；
5. 底部固定审核操作区（仅待提交时出现）。

审核操作区：

```text
[驳回] [通过]
```

- 点击“通过”：弹出确认框，文案为 `确认通过「{服务商名称}」的准入申请？`；确认后状态变为 `已通过`，写入审核历史。
- 点击“驳回”：打开小弹窗，仅含“驳回原因”多行输入框；为空不可提交；确认后状态变为 `已驳回`，写入审核历史。
- 不引入多级审批、风险例外、合同生效或第二次确认流程。

## 6. 数据模型与实现要求

### 6.1 建议最小类型

现有 `Vendor` 类型字段可以临时保留以避免影响其它页面，但服务商准入页面不得再读取或展示无关字段。为本页建立或收敛为以下读取模型：

```ts
type VendorAccessStatus = '草稿' | '待提交' | '已通过' | '已驳回'

interface VendorAccessRecord {
  id: string
  vendorId: string
  vendorName: string
  creditCode: string
  legalRep: string
  address: string
  contactName: string
  contactMobile: string
  businessLicenseFile: string
  status: VendorAccessStatus
  submittedAt?: string
  reviewedAt?: string
  reviewedBy?: string
  rejectionReason?: string
  history: VendorAccessHistory[]
}

interface VendorAccessHistory {
  id: string
  action: '保存草稿' | '提交' | '通过' | '驳回'
  operator: string
  role: '服务提供商' | '药厂合规部门'
  time: string
  comment?: string
}
```

### 6.2 数据归属和联动边界

- 记录应放在共享 context/store 中，而不是仅 `VendorAccessManage.tsx` 的 `useState`；同一会话内角色切换后，服务商提交的数据必须能被合规端立即看到。
- 本次不将该记录接入 `TaskExecution`、`Settlement`、`BudgetPlan`、`VarietyAuth` 或医药代表备案；不要新增“准入拦截”假逻辑。
- 若原有 `Vendor` 仍被代表备案等页面引用，禁止删除现有字段或更改其 ID；新增轻量准入记录可通过 `vendorId` 关联。
- 种子数据至少准备四条：服务商自己的草稿、待审核、已驳回、已通过；不同状态必须能完整演示两端路径。

### 6.3 菜单与权限实现

- 菜单可见性必须同时受 `hideForRoles` 与 `PermissionContext` 的页面权限约束；不能只靠 UI 隐藏。
- 为两个角色显式授予 `vendor-access` 的 `view`：服务商还需要 `create`、`edit`、`submit`；合规需要 `approve`。
- 组件内仍需做角色校验，防止手工路由切换看到不属于自己的操作按钮。
- 将药厂销售端的 `vendor-access` 权限移除或改为仅不可见，保证无法通过全局搜索进入。

## 9. 完成定义

执行 AI 完成后，必须提供：

1. 修改文件清单；
2. 两个角色的实际截图或可复现路径；
3. `npx tsc --noEmit` 通过结果；
4. `pnpm build` 通过结果；
5. 第 8 章 A01–A13 的逐项验证结果。

审核标准不是“页面更好看”，而是：只有服务商提交、药厂合规通过/驳回两类动作；所有菜单、按钮、状态、详情和权限都服务于这条闭环。
