# 多租户平台企业码与服务商可见范围 · 深度审核与解决方案

> 审核日期：2026-09-15  
> 审核范围：平台运营租户管理、企业码、首位管理员激活、租户生命周期、服务商人员对合作药厂的可见范围，以及相关登录和交互设计。  
> 结论：当前原型已具备“平台创建租户 → 企业码登录 → 首位管理员激活”的骨架，但实现混入了并未确认的“申请审核、补正、企业码别名、激活提醒重发”机制；更关键的是，**服务商内部人员可以看见哪些合作药厂，尚未建立独立且可审计的授权模型**。因此现阶段不能称为完整定版。

---

## 一、最终设计结论

### 1.1 租户开户应改为“平台直接创建”，不是“申请审核”

平台运营是内部运营角色，创建药厂或服务商属于平台侧的主数据开户行为，不应套用外部企业的“申请—审核—补正”流程。

最终主流程应为：

```text
平台运营新建租户
  → 填写主体资料和首位管理员
  → 系统做格式、重复主体、必填字段校验
  → 确认创建
  → 原子创建企业根组织、主企业码、首位管理员待激活关系和基础角色
  → 显示企业码
  → 首位管理员用“企业码 + 手机号 + 验证码”首次登录
  → 首次登录自动激活管理员和租户
```

这里的“主体资料”是平台留档和基础校验，不等同于平台内置的审核工作流。工商或商务核验如有需要，应在线下或未来独立能力完成，不能在本期租户管理里伪装成完整审核系统。

### 1.2 企业码只保留一个主码

企业码用于用户定位租户，越简单越好。一个租户一个主码即可：

- 系统自动生成 8 位无业务语义编码；
- 平台运营只能复制和查看，不能手工编辑或重新生成；
- 终止租户后该码永久保留，不重新分配；
- 暂停租户时该码禁止新登录；恢复后恢复解析；
- 不做别名码、别名申请、别名停用、别名审计和别名登录解析。

删除别名不会损失本期核心价值，反而减少用户记忆、客服解释、迁移、审计和登录解析的复杂度。

### 1.3 服务商“可见药厂”不能放进角色数据范围

角色管理中的“数据范围”回答的是：**这个角色在本服务商内部能看哪些组织、部门、工作组或人员的数据。**

“可以进入或看见哪家合作药厂”回答的是：**服务商内部的哪个部门、工作组或人员，获准在当前有效合作关系下服务哪家药厂。**

两者是不同维度，不能合并为一个角色字段。把合作药厂可见性直接塞进角色数据范围，会导致：

1. 一个角色调整范围时，意外改变一批人可进入的药厂；
2. 同一角色无法区分华东团队看 A 药厂、华南团队看 B 药厂；
3. 角色复制、临时授权和组织调整会造成跨药厂数据泄露；
4. 无法解释“是角色变化、部门变化还是合作关系变化”导致可见范围改变；
5. 审计记录和影响提示无法准确落到“哪家药厂”。

正确方案是新增独立的“合作药厂与服务范围授权”能力；角色管理只展示只读提醒和跳转入口。

## 三、租户管理简化后的页面设计

### 3.1 租户列表

保留表格形式，删除“申请状态”列、筛选和统计卡。建议字段：

| 企业名称 | 类型 | 统一社会信用代码 | 主企业码 | 首位管理员 | 租户状态 | 创建时间 | 操作 |
| --- | --- | --- | --- | --- | --- | --- | --- |

状态统计只保留：待激活、正常、已暂停、已终止。

列表操作：

- 待激活：详情；
- 正常：详情；
- 已暂停：详情；
- 已终止：详情（只读）。

“新建租户”不再生成申请单，直接进入创建向导。

### 3.2 新建租户向导

保留三步，不保存草稿：

1. 选择类型：药厂 / 服务提供商。
2. 填写企业资料：企业名称、简称、统一社会信用代码、地址、联系人、联系人手机号、备注；药厂按需要保留药厂资质字段，服务商移除“服务类型/经营范围”，营业执照或证明材料为选填。
3. 指定首位管理员并确认创建。

确认文案：

> 确认创建后，系统将生成不可修改的主企业码，并创建首位管理员待激活账号。

创建完成页只展示：企业名称、类型、主企业码、首位管理员姓名和脱敏手机号、当前状态“待激活”。

### 3.3 租户详情

详情头部固定展示：企业名称、类型、租户状态、主企业码、复制按钮。

保留三个页签即可：

1. 基本信息：主体资料、首位管理员、状态操作。
2. 管理员与成员：表格展示。
3. 操作日志：创建、复制主码、管理员变更、状态变更、激活。

删除：

- 企业码管理页签；
- 别名码区块；
- 状态与生命周期页签；
- 重发激活提醒；
- 提交与审核历史、补正入口。

### 3.4 租户状态操作

| 当前状态 | 可执行操作 | 必填记录 | 后果 |
| --- | --- | --- | --- |
| 待激活 | 变更首位管理员 | 变更原因 | 新管理员成为待激活；旧管理员失去初始管理员资格 |
| 正常 | 暂停租户 | 原因码 + 说明 | 禁止新登录；已有会话在生产端下次请求失效 |
| 已暂停 | 恢复租户、终止租户 | 原因码 + 说明 | 恢复时重新计算当前有效授权；终止后不可恢复 |
| 已终止 | 无 | — | 只读，主企业码永久失效 |

“正常”不是可由平台直接选择的初始状态；必须由首位管理员首次登录激活后获得。

## 四、待激活管理员完整体验

### 4.1 药厂管理员

```text
体验演示账号：待激活药厂管理员
  → 自动填充药厂主企业码和手机号
  → 发送验证码
  → 输入 123456
  → 展示 Toast：账号已激活，欢迎加入
  → 单角色直接进入药厂工作台
  → 平台租户列表中该租户状态改为“正常”
```

### 4.2 服务商管理员

```text
体验演示账号：待激活服务商管理员
  → 自动填充服务商主企业码和手机号
  → 发送验证码
  → 输入 123456
  → 展示 Toast：账号已激活，欢迎加入
  → 单角色直接进入服务商工作台
  → 平台租户列表中该租户状态改为“正常”
```

规则：

- 待激活只在验证码成功后披露；请求验证码阶段不得泄露账号状态。
- 激活提示只出现一次。
- 演示环境提供“恢复演示数据”后可重新演示待激活路径；生产环境不提供该入口。
- 删除“重发激活提醒”不影响该流程，因为首次登录本身就是激活触发点。

## 五、服务商不同部门可见合作药厂：推荐设计

### 5.1 模型：合作关系与人员范围授权分层

必须同时满足四层条件，用户才可在“选择服务药厂”页面看见并进入某药厂：

```text
服务商成员身份有效
  ∩ 药厂—服务商合作关系有效
  ∩ 服务商内部获得该药厂的服务范围授权
  ∩ 该药厂下的品种/区域等业务授权有效
```

备案状态不参与“是否看得见药厂”的判定；备案待审、补正、过期或暂停只限制学术拜访，仍可进入药厂空间查看通知和补充资料。

### 5.2 权限归属

| 权限层 | 谁管理 | 控制什么 |
| --- | --- | --- |
| 药厂—服务商合作关系 | 药厂 | 是否允许该服务商整体服务本药厂；暂停立即切断所有人员 |
| 品种、区域等业务授权 | 药厂 | 服务商在药厂下可承接什么业务范围 |
| 部门/工作组/人员对合作药厂的可见与进入范围 | 服务商管理员 | 哪些内部团队能看见、进入和实际服务哪家药厂 |
| 角色数据范围 | 服务商管理员 | 一个角色在服务商内部可查看哪些部门、人员和数据，不控制药厂对象 |
| 备案 | 药厂 | 是否允许特定服务专员开展学术拜访，不控制药厂可见性 |

药厂保留最终上游控制权：合作暂停或品种授权撤销后，服务商内部无论如何分配，都不能继续进入或开展对应业务。

### 5.3 新增页面：合作药厂与服务范围授权

建议入口：

```text
服务商工作台
→ 系统管理 / 权限管理
→ 合作药厂与服务范围授权
```

不要放在“角色管理”的配置页内。角色管理可增加只读说明和跳转链接：

> 本角色的数据范围不决定可见合作药厂。请在“合作药厂与服务范围授权”中配置部门、工作组和人员可服务的药厂。

页面布局建议：

1. 顶部：当前服务商、有效合作药厂数量、待处理异常数量。
2. 左侧：服务商组织树，支持选择部门、工作组或个人。
3. 右侧：合作药厂表格，列为药厂、合作状态、品种授权状态、已授权对象数、有效期、操作。
4. 主操作：“配置可服务药厂”。
5. 配置弹窗：选择对象、勾选有效合作药厂、设置有效期、填写原因/备注。
6. 保存前展示影响预览：将新增或移除多少名成员可见的药厂、是否影响正在服务的药厂上下文。

### 5.4 授权对象和生效规则

支持的主体：服务商、部门、工作组、个人。

首期推荐规则：

1. 服务商管理员默认能看到本服务商全部有效合作药厂，用于管理和分配。
2. 非管理员默认不显示任何合作药厂，必须获得部门、工作组或个人授权。
3. 同一用户同时命中部门、工作组、个人授权时取并集。
4. 首期不做“拒绝规则”；若要排除部门中某个人，使用个人授权配置或调整其组织归属。后续确有大量例外时再增加显式排除规则。
5. 授权有起止日期，到期自动失效。
6. 合作暂停、品种授权失效、用户停用、角色失效时，不论内部授权是否还在，均实时失效。
7. 用户当前正在操作的药厂被收回时，下一次请求强制刷新上下文并提示“该药厂服务范围已调整，请重新选择”。

建议数据模型：

```ts
interface ProviderPharmaScopeGrant {
  id: string
  providerId: string
  pharmaId: string
  subjectType: "department" | "group" | "user"
  subjectId: string
  effectiveFrom: string
  effectiveTo?: string
  status: "active" | "revoked" | "expired"
  grantedBy: string
  grantedAt: string
  reason: string
}
```

### 5.5 用户提示和审计

配置前必须显示影响：

- “授权华东推广部后，该部门下 18 名有效成员将在下次刷新或重新登录后看见并可选择百益制药。”
- “收回工作组一对百益制药的授权后，6 名成员不能再进入该药厂；已有草稿按业务规则保留但不可继续提交。”
- “合作关系已暂停，内部授权不会恢复任何人员的进入权限。”

以下动作必须填写原因并写审计：

- 批量新增或收回药厂范围；
- 影响 5 人及以上的范围变更；
- 收回某人当前正在服务的药厂；
- 调整有效期；
- 直接授予个人例外权限。

审计字段：操作者、服务商、对象类型与对象、药厂、变更前后范围、受影响成员数、原因、时间、requestId。

## 六、关键状态判定

服务专员登录服务商后，服务药厂门页应基于如下派生函数，而不是单看角色或单看合作关系：

```text
canSeePharma(user, pharma) =
  用户在服务商内为有效成员
  AND 服务商—药厂合作关系有效
  AND 用户命中该药厂的内部服务范围授权

canEnterPharma(user, pharma) =
  canSeePharma(user, pharma)
  AND 人员/部门范围有效
  AND 至少存在有效业务授权

canAcademicVisit(user, pharma) =
  canEnterPharma(user, pharma)
  AND 备案状态有效
```

门页表现：

| 条件 | 是否展示 | 是否可进入 | 提示 |
| --- | --- | --- | --- |
| 未获得服务范围授权 | 不展示 | 否 | 不向普通人员暴露该药厂 |
| 合作暂停 | 已获授权人员可见禁用卡 | 否 | 合作已暂停，暂时无法进入 |
| 无有效品种/人员范围 | 已获授权人员可见禁用卡 | 否 | 当前没有有效的服务范围或品种授权 |
| 备案待审/补正/过期/暂停 | 展示警告卡 | 是 | 可进入查看通知和补料，暂不可开展学术拜访 |
| 全部有效 | 展示可选卡 | 是 | 正常进入 |

平台跨药厂运营分析是单独的聚合权限，不得因为服务商管理员能看到多家药厂，就自动获得跨药厂分析数据。

## 七、界面和可用性整改细则

### 7.1 角色确认页

- 身份确认信息改为标签和值的两行结构，避免长句换行。
- 已认证手机号只显示脱敏号码。
- 企业名称可换行，企业码不得被拆分。
- 角色卡片标题 16–18px、辅助信息不少于 13px。
- 中文标题和说明使用 `letter-spacing: 0`；只有企业码使用正字距。

### 7.2 租户管理列表

- 使用租户状态而非申请状态。
- 增加一条“正常”租户，统计不能显示 0。
- 空态、筛选无结果、加载失败三种状态必须区分。
- 表格在窄屏使用横向滚动或卡片模式，不能裁切。
- “恢复演示数据”仅演示环境可见，旁边说明会重置本地模拟数据。

### 7.3 详情页

- 状态操作放在头部，和当前状态标签并列。
- 暂停、恢复、终止均二次确认，必须填写原因码和文字说明。
- “管理员与成员”改为表格；空态明确说明正式租户首期仅预置首位管理员，后续成员由企业管理员维护。
- 操作日志按时间倒序展示，支持查看原因和影响摘要。

### 7.4 视觉基础规则

- 正文 14px，辅助文字 12–13px，避免 10–11px 中文业务文案。
- 统一 4px/8px 间距节奏。
- 普通文字对比度目标不低于 4.5:1；警告、成功、错误不能只用颜色表达。
- 所有图标按钮有可读名称和焦点环。
- 320px、390px、768px、1024px、1280px、1440px 必须实测。

## 八、实施顺序

### 第一批：收敛错误的业务模型（P0）

1. 删除别名码全链路。
2. 删除申请、审核、驳回、补正及申请状态。
3. 把注册表状态简化为 `pending_activation / active / suspended / terminated`。

5. 在详情头部落地状态切换和原因审计。
6. 新增服务商合作药厂范围授权模型和最小页面，不把它塞进角色数据范围。

1. 增加正常租户种子数据。

5. 服务商创建表单移除服务类型，将营业执照改为选填。

## 十、生产落地边界

本原型可以展示完整业务体验，但以下能力必须由服务端实现后才具备真正安全性：

1. 企业码全局唯一和不可复用约束。
2. 租户创建、组织创建、首位管理员创建、主码生成的数据库事务和幂等键。
3. 登录、会话换发和每一次业务接口对租户状态的校验。
4. 服务商合作药厂范围授权的服务端数据过滤，不能仅依赖前端隐藏。
5. 手机号、证照、日志和导出的脱敏及访问审计。

在生产实现前，前端中的 `localStorage`、模拟短信、演示数据重置仅能作为演示工具，不能被视为安全控制。

## 十一、审核最终判定

当前版本的优点是：已经把企业码、首位管理员、租户状态和登录网关串起来，并具备运行时原型闭环。

但当前版本的问题不是“少几个按钮”，而是包含了未被业务确认的流程，且遗漏了真正决定跨租户数据边界的服务商—药厂人员范围授权。

完成本文件第一批整改后，系统才能形成正确的最小闭环：

```text
平台直接创建药厂/服务商
→ 系统发放唯一主企业码
→ 首位管理员激活
→ 药厂控制合作关系和业务授权
→ 服务商控制内部部门/人员服务哪些合作药厂
→ 每次进入药厂都按四层条件实时派生权限
```

在“合作药厂与服务范围授权”落地前，不应宣称已经解决服务商内部不同部门、工作组和人员对药厂数据的隔离问题。
