# 药合作系统 — 重构范围与信息架构说明

> 唯一事实来源：`/Users/lee/本地/Obsidian Vault/重构/字段采集结果.md`（53 个叶子页）
> 本文定位：**不照搬旧菜单**，围绕业务主线「任务配置 → 一线填报 → 审核 → 绩效/结算 → 证据链」输出重构范围与信息架构。

## 0. 现状理解（一句话）

旧系统把「同一业务链路的多个环节」按「综合业务 / 个人业务 / 任务管理 / 绩效管理」等**模糊维度**拆成了并列菜单，导致：
- 「工作组报告」（综合业务 8 页）与「服务专员 XX 信息收集」（个人业务 4 页）是**同一类报告业务的两侧视角**，被拆散在两级菜单；
- 拜访 3 类、调研 5 类、报告 8 类字段结构高度雷同，却各自独立成页；
- 审核/绩效/结算分散在各业务列表内，无统一入口；
- 「服务专员 / 工作组 / 服务提供商 / 药厂用户」4 页实为同一页面 `userListUI?userType=X`，重复铺开。

重构目标：**按业务主线聚合页面、按角色收敛视角、把状态流转显性化**。

## 2. 新信息架构

### 2.1 设计原则
1. 一级导航按**业务主线阶段**组织，不按「综合/个人」等角色模糊词。
2. 字段雷同的页面合并，用「业务类型」维度区分；明细字段差异大的，共享框架、保留各自表单。
3. 状态流转（提交/审核/驳回/撤销/结算）统一到状态机，各业务页面复用同一套规则。

## 4. 核心业务状态机

### 4.1 业务单据状态机（拜访/调研/会议/问卷/随访/流向/库存/准入/报告）

```
        ┌────────────── 撤销(撤回) ──────────────┐
        │                                          │
   草稿 ──提交──▶ 待审核 ──审核通过──▶ 已通过 ──打绩效──▶ 已打绩效 ──结算──▶ 已结算
   (保存)          │                                          ▲
                   ├──审核驳回──▶ 已驳回 ──修改后重新提交──▶ 待审核
                   └──删除(仅草稿/未审核)
```

状态枚举（从采集结果可坐实的字段）：
- **审核状态**：待审核 / 已通过 / 已驳回（字段「审核状态」+ 按钮「批量审核通过/驳回」）
- **绩效状态**：未生效 / 已生效（字段「绩效状态」选项）
- **是否已打绩效**：是 / 否（字段「是否已打绩效」）

各字段完整枚举值未在采集结果中全量拿到，**状态取值以研发/生产库为准**【待业务确认】。

### 4.2 任务状态机（推广任务 / 报告问卷任务）

```
   草稿 ──发包(下发)──▶ 已下发 ──填报──▶ 填报中 ──提交──▶ 待审核 ──通过──▶ 已通过 ──结算──▶ 结算中 ──完结──▶ 结算完结
                                      │                ├─驳回──▶ 调整 ──▶ 重新提交
                                      │                └─撤销任务──▶ 作废
```

任务页字段可见「任务状态」「对账状态」两个独立状态，**两者的精确枚举与联动关系未坐实**【待业务确认】。

### 4.3 结算单状态机

```
   待结算 ──生成结算单──▶ 待确认 ──确认结算单──▶ 已确认 ──上传付款凭证──▶ 已支付 ──▶ 结算完结
                          │
                          └──调整──▶ 重新生成（差额/调整原因字段可见）
```

### 4.4 关键动作规则说明

| 动作 | 规则（基于采集结果，未坐实处标注） |
|---|---|
| **提交** | 业务单据从草稿进入待审核；多数业务页含「提交」按钮，审核前数据可反复保存【提交后是否锁定编辑待确认】 |
| **审核通过** | 单据进入已通过，可打绩效；支持「批量审核通过」 |
| **驳回** | 驳回需填「审核意见」，驳回后进入已驳回态，可修改重新提交；「审核意见(驳回时必须)」为必填项（任务下发页可见） |
| **撤销** | 会议/义诊页可见「撤销」行操作；撤销的**时机窗口（哪些状态可撤）与后果（是否影响绩效）未坐实**【待业务确认】 |
| **结算完结** | 任务页可见「结算完结」行操作；完结后**是否可回退、是否锁定相关单据**未坐实**【待业务确认】 |
| **删除** | 多数列表有删除/批量删除；危险操作，采集时未执行，**删除前置条件（是否仅限草稿）未坐实**【待业务确认】 |

## 6. 待业务确认清单（汇总）

> 以下为本文所有未坐实事项，需业务/研发逐条拍板，不得据此开发。

1. **状态枚举**：审核状态、绩效状态、任务状态、对账状态、结算状态各自的完整取值与中文名。
2. **撤销规则**：哪些状态允许撤销；撤销后对已打绩效、对账的影响。
3. **驳回粒度**：驳回是整单驳回，还是支持部分驳回；驳回后重提是否保留原审核意见。
4. **审核层级**：初审在「工作组」还是「平台运营」；是否存在两级审核。
5. **绩效与审核先后**：是否严格「先审核通过，后打绩效」；驳回是否回退绩效。
6. **结算完结回退**：结算完结后能否回退；完结是否锁定任务与单据。
7. **删除前置条件**：删除是否仅限草稿/未审核态；删除是否物理删除或逻辑作废。
8. **「我的业务开关」vs「药厂业务开关配置」**：是否同一配置的两个视角，是否合并。
9. **「品种资料维护」vs「品种管理」**：附件是否作为品种明细 Tab 并入。
10. **「问卷调查题目管理」vs「问卷管理」**：题目是否并入问卷作明细。
11. **服务专员报告收集（4页）vs 工作组报告（8页）**：合并为「报告」两级视图后，是否需要分角色页面，还是统一列表+权限过滤。
12. **调研 5 类聚合力度**：是统一列表（类型字段区分）还是保留各自表单（Tab/子类型）。
13. **会议报告管理归属**：归「会议活动」还是「报告管理」。
14. **任务下发 vs 推广任务分配**：是否统一为「任务中心」用任务类型区分，还是保留两个独立流程。
15. **结算口径**：结算单金额 vs 凭证生成金额的关系。
16. **审核中心**：二期是否做统一审核工作台，还是长期保留各列表内审核。
17. **角色权限边界**：各业务页初审归属、服务商下属管理范围、药厂可见数据范围。
18. **统一审核中心 / 各列表审核** 的取舍影响 MVP 范围。
