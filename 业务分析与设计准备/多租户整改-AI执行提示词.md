## 〇、业务拍板与演示口径（全局，不得推翻）

1. **登录方式**：只用**企业编码 + 手机号 + 短信验证码**；密码、企业微信、微信扫码入口本期隐藏（代码保留，开关控制）。
2. **服务专员仅 APP 是生产口径**；原型以 Web 登录链路**兼任**该流程的演示通道：MOBILE 档专员名下有服务药厂授权即放行进入 Web 三步流，`PharmaGate` 即「APP 服务药厂中间页」的替身（沿用现状，不得改动）。**不引入 clientType/web/app 区分**，真实 APP 接入是批次外事项。
3. **备案仅拦学术拜访，不拦进药厂**：未备案/待审/补正/过期/被暂停备案的服务专员**可以进入药厂业务空间**（登录、通知、补料照常），只在学术拜访入口拦截（拜访拦截属批次③）。门页上备案状态只表现为**警告标识**，见 F。
4. **证件材料在线直接展示、不脱敏**（查看留痕口径在后续批次体现）。
5. **导出不做事前审批**，走事后审计口径；完整身份证号导出路径本期不提供（批次④落地脱敏锁定）。
6. **合作暂停/恢复不回写子授权状态**，按「合作生效 ∧ 自身状态有效 ∧ 未过期」实时派生判定（批次②在授权页落地展示态）。
7. **入口区分**：普通平台侧角色（平台运营、系统管理员、平台下的账户管理员）走**平台企业的企业编码 + 验证码**，与药厂/服务商同链路；**超级管理员**（批次④新增的独立治理账号）不走企业编码通道，走平台后台独立入口（密码+验证码双因子）。两者不是同一类账号，不得混淆。

## 二、批次① 改动点规格：登录与门页

### A. 企业编码第 1 步（LoginPage 登录卡内前置）

1. 在 `authProfiles.ts` 新增企业编码登记表（原型口径，生产由平台运营生成）：
   - 为 `PERM_ORGS` 中每个企业根节点登记一条**主编码**：8 位大写字母数字、无业务语义（如 `E9K4P7X2` 风格）、排除易混字符（0/O、1/I）；平台/药厂/服务商共用同一编号空间。
   - 结构建议：`ENTERPRISE_CODES: EnterpriseCodeEntry[]`，字段含 `code`、`enterpriseId`（对应企业根 orgId）、`status: "primary" | "alias"`、`enabled`。**为其中一个药厂配一条演示别名**（alias 指向同一 enterpriseId）。
2. 登录卡两段式：
   - **第 1 段**：企业编码输入 + 「本设备记住的企业」快捷条目（显示企业名，点击选中；每条可删除；保留「输入其他企业编码」手动入口）。校验通过显示企业名称（只显示名称，不显示类型/成员数），进入第 2 段；顶部「切换企业」返回链接。
   - **第 2 段**：手机号 + 验证码（沿用现有 sms 面板交互：6 位分格、60s 重发、模拟短信回显卡）。
   - **切换企业时必须清空**：手机号、验证码分格、重发倒计时、演示验证码回显；**并丢弃所有未返回的旧请求结果**（用递增序号/令牌守卫，防止慢返回的旧 `resolveEnterprise`/`requestSms` 覆盖新企业状态）。
3. 记住企业存 localStorage（编码+企业名），**读写全部 try/catch**：不可用、格式损坏或写入失败时静默降级，登录流程不受影响。**快捷条目仅用于回填编码**：点击后仍必须重新调用 `resolveEnterprise` 解析，不得信任缓存中的企业名/ID；解析失败时静默删除该条并提示重输。编码统一 `trim().toUpperCase()` 归一化。退出登录不清除记忆。
4. 解析失败统一文案：「企业编码不存在或已停用，请核对后重试」（不存在/停用不区分）。
5. 步骤口径：登录卡内完成「1 企业验证 → 2 短信验证」；门页步数文案相应改（见 E）。

### B. 登录方式收敛

1. 登录卡**只露出短信验证**：去掉页签切换 UI，短信面板为默认且唯一面板。
2. 密码与扫码的组件逻辑、契约方法、`QR_IDENTITIES`、演示二维码组件**全部保留**，以模块级开关控制露出（如 `LOGIN_METHODS_EXPOSED = { password: false, qr: false }`）。**开关关闭时不只是不渲染入口：不得创建二维码票据、不得启动轮询定时器、不得执行任何隐藏方式的副作用**（现登录页挂载即建码轮询，必须用同一开关把 `createQrTicket` 的 useEffect 一并门控）。
3. 开关重新打开（回归用）的口径：旧面板恢复渲染即可，**不要求密码/扫码接入企业编码前置链路**，保持原实现并加注释「非本期口径，仅回归验证」。
4. 「体验演示账号」速查改造：每条展示**企业编码 + 手机号**（去掉统一密码行）；点击 = 填好编码并解析出企业名、填好手机号，停留在短信段待发送。`DEMO_ACCOUNT_HINTS` 补充 `enterpriseCode` 与 `phone`，scene 同步改写。
5. 陈伟 scene 改为双企业口径：「用东方恒业编码登录=服务商管理员；用百益制药编码登录=药厂合规」。

### C. 企业内手机号、防枚举与企业上下文（mockGateway 核心改造）

1. `requestSms/verifySms` 契约入参增加 `enterpriseId`（登录页第 1 段解析结果传入）。
2. **企业成员判定（明确规则）**：手机号命中的用户满足以下任一条即为本企业成员——① `enterpriseRootOf(PERM_ORGS, user.orgId)` 等于该企业根；② 该用户在 `seedAssignments` 中存在 scopeOrgId 落在该企业组织树内的授权记录。角色是否可登录由授权状态（active/过期/回收）**单独判定**，与成员判定分离。
3. **短信票据绑定企业**：`smsTickets` 键改为 `${enterpriseId}:${phone}`（或票据内记录 enterpriseId 并校验时比对）。同一手机号在两个企业先后请求互不覆盖、互不串用；重发覆盖旧票据（旧验证码即失效）。
4. **请求阶段不做成员与状态判断**：手机号格式合法一律返回统一成功态 + 演示验证码（非成员返回「假码」）。移除 `requestSms` 里对 `resolvePrincipal` 的调用及其差异化失败。
5. **状态披露时点 = 验证码校验成功之后**：
   - 非本企业成员（或不存在）→ 校验时以「验证码不正确，还可尝试 N 次」失败→ 耗尽作废，**不出现任何「手机号不属于本企业/未绑定」类可枚举提示**；
   - 本企业成员但冻结 → 校验成功后提示「该账号已被冻结，请联系企业管理员」；
   - 已停用 → 校验成功后沿用现有停用文案；
   - 待激活 → 校验成功后放行并激活（见 D）。
6. **企业上下文贯穿整条链路**：`enterpriseId` 作为参数贯穿 `resolvePrincipal` / `identityOptionsFor` / `chooseLoginIdentity`——身份选项、角色确认、会话签发全部限定在本次认证企业内，任何一步不得退回「按 userId 全量重查」。
7. **身份选项去重（保守口径）**：仅合并「enterpriseId + roleId + scope + scopeOrgId 完全相同」的真重复授权；**范围不同的同角色授权保留为独立选项**（现有选项已展示 scopeOrgName，天然可区分），不得用「取最新一条」代表整个角色——范围合并/并集计算属批次②权限改造，本批不做。

### D. 账号状态演示（待激活/冻结，企业级）

1. 成员状态改为**企业级**：`AuthProfile` 扩展 `memberStatusByEnterprise?: Record<string /*enterpriseId*/, "pending_activation" | "frozen">`（原型口径；**不改 `PERM_USERS.accountStatus` 枚举**，避免波及用户与组织页，那属批次②）。陈伟这类双企业身份在一边冻结不得影响另一边。
2. 行为（披露均在验证码校验成功后，见 C-5）：
   - `pending_activation`：放行 + 内存态置为正常 + **会话携带一次性 `activationNotice` 字段，由 Root/业务壳层挂载时消费并 toast「账号已激活，欢迎加入」**（登录页组件在 setSession 后即卸载，不得依赖登录页自身显示 toast）；审计「首次登录激活」。**持久范围 = 内存态（同一运行周期）**，刷新回到待激活属预期。
   - `frozen`：拒绝，文案「该账号已被冻结，请联系企业管理员」，审计拒绝。
3. **演示账号必须落完整数据链**（四处齐落：`PERM_USERS`（orgId 挂对应企业组织）→ `seedAssignments`（该企业内一条 active 授权）→ `AUTH_PROFILES` → `DEMO_ACCOUNT_HINTS`）。本批需要：服务商侧待激活新成员 1 名、冻结成员 1 名（仅在其所属企业被拒）、全不可用药厂的服务专员 1 名（孙琪，见 F-5）。

### E. 三步流第二步语义调整（IdentityConfirmGate）

1. 改为**企业内角色确认**：标题/副标题从「选择所属企业」改为「选择本次使用的角色」；选项 = C-6/C-7 口径。
2. 单角色：**由网关直接签发 `identityConfirmed: true`**，不闪现角色确认页再自动跳转；多角色（同企业两个不同角色）出选择器。
3. 双企业身份（陈伟）：不在第二步跨企业切换，回登录页换企业编码；门页「更换账号」链接送回登录卡第 1 段。
4. 步数文案统一为四步口径：企业验证 → 短信验证 → 角色确认（单角色隐藏）→ 选择服务药厂（仅服务专员）。

### F. 选药厂门页：状态模型重做、备案警告与直达规则（PharmaGate）

1. **状态模型拆成两类**：
   ```ts
   type BlockedKind = "cooperation_paused" | "no_valid_variety" | "no_scope"
   type WarningKind = "filing_pending" | "filing_rejected" | "filing_expired" | "filing_suspended"
   ```
   - `ServingPharma.status` 恢复纯合作语义 `"active" | "paused"`；新增可选 `blockedKind?: BlockedKind` 与 `warningKind?: WarningKind`（互斥，blockedKind 优先）。
   - **进入条件（派生函数 `enterablePharma(p)`）**：`p.status === "active" && !p.blockedKind`。**warningKind 不参与进入判定**——备案状态只警告、不阻断（拍板口径）。
   - 原先所有用 `status === "active"` 判「可进入」的位置（`resolvePrincipal` 专员放行、`identityOptionsFor` 的 MOBILE 跳过、PharmaGate 分组、`chooseServingPharma` 拒绝、切换浮层）统一改用 `enterablePharma`。
2. **卡片行为与文案**：

   | 状态 | 卡片行为 | 用户提示 |
   | --- | --- | --- |
   | 合作暂停（status=paused 或 blockedKind） | 禁止进入 | 合作已暂停，暂时无法进入。请联系企业管理员。 |
   | 无有效品种（no_valid_variety） | 禁止进入 | 当前没有有效的品种授权，请联系企业管理员。 |
   | 无人员范围（no_scope） | 禁止进入 | 尚未分配该药厂的服务范围，请联系企业管理员。 |
   | 备案待审核（filing_pending） | **可以进入**，警告标识 | 备案正在审核中，可查看通知和补充材料，暂不可开展学术拜访。 |
   | 备案被退回（filing_rejected） | **可以进入**，警告标识 | 备案材料需要补正，请查看审核意见并重新提交；暂不可开展学术拜访。 |
   | 备案过期/暂停（filing_expired / filing_suspended） | **可以进入**，警告标识 | 当前备案已失效，重新生效前不可开展学术拜访。 |

   - `pausedReason` 等**不得直接外显内部审批意见**：demo 数据里该字段一律填写「已适合对外展示的文案」，字段注释注明；生产口径为原因码→标准文案映射。
3. **直达/展示规则（修正现逻辑）**：仅当**名下服务药厂总记录 = 1 且可进入**时走单药厂直达；**总记录 > 1 时一律展示完整门页**（可进入卡 + 警告卡 + 禁用卡并列，即使可进入的只有一家）——保证不可用原因始终可见。
4. **空态可达**：专员放行条件从「有 active 药厂」改为「名下存在服务药厂记录（含不可用）」——全部不可用时仍完成认证并进门页，展示空态卡「当前没有可进入的服务药厂」+ 不可用清单（企业名 + 原因标签）。`role-mobile-only` 拦截仅当「名下完全没有服务药厂记录」时触发，**文案改为「尚未配置服务药厂，请联系企业管理员」**（原「请使用药友料 App 登录」与 Web 兼任演示通道的口径矛盾，废弃）。
5. **演示数据（不新增任何企业/组织节点）**：
   - 杨明：百益 active（正常进入）；华康 `filing_pending`（**可进入 + 备案警告**）；康宁 `paused`（合作暂停）→ 三卡并列展示完整门页。
   - 新增专员**孙琪**（完整数据链见 D-3）：百益 `no_scope`、华康 `no_valid_variety`、康宁 `paused` → 三家全不可用，走空态演示。
   - 黄峰不变（1 条记录且可进入 → 单药厂直达）。

### G. 会话签发与契约同步

1. **`chooseServingPharma` 不得重新 `resolvePrincipal(userId)`**（会把已选角色弹回默认主角色）：基于当前会话 principal（或显式传入 assignmentId/roleId/enterpriseId）签发，仅叠加 servingPharma 字段。
2. `authTypes.ts` 头部「生产接入」注释补充：企业编码解析、企业内手机号归属校验、账号状态拦截、短信票据管理在生产全部由服务端完成。
3. 新增契约方法 `resolveEnterprise({ code })` → `{ enterpriseId, enterpriseName }`（非敏感展示信息）或统一失败。
4. **审计事件矩阵（全部落 `pushLoginAudit`，`reason` 存标准原因码而非中文文案）**：

   | 事件 | 原因码示例 |
   | --- | --- |
   | 企业编码解析失败 | `ENT_CODE_INVALID` |
   | 验证码请求（成功/假码） | `SMS_SENT` / `SMS_SENT_DECOY` |
